### 4.3 책임 범위 분리
| 기능 | 현재 워크플로우 | 제안된 n8n 워크플로우 | 중복 여부 |
|------|----------------|----------------------|-----------|

| AI 분석 및 주도주 선정 | ❌ 없음 | ✅ n8n + OpenRouter (Nemotron) | ❌ 없음 |
| 실시간 매매 로직 실행 | ❌ 현재 주문 차단 중 | ✅ 로컬 파이썬 스켈핑 봇 | ❌ 없음 |
| 장중 감시 및 알림 | ✅ Hermes cron (OR10/OR30, 타이밍 알림) | ❌ 없음 | ❌ 없음 |
| 일일 리포트 및 피드백 | ✅ Hermes cron (백테스트 준비도, PnL) | ❌ 없음 (또는 선택적 피드백 루프) | ❌ 없음 |
| 주문 실행 게이트 | ❌ 차단 중 (백테스트/paper 게이트 미통과) | ❌ 차단 중 (동일 게이트 적용 필요) | ✅ **같은 게이트**이지만 **실행 주체 다름** |

**중복 가능성 있는 점**: 주문 실행 게이트 자체는 동일하다. 그러나 현재 시스템은 **주문이 차단된 상태**이며, 제안된 워크플로우는 **아직 게이트를 통과하지 않은 상태**에서 시뮬레이션 또는 페이퍼 트레이딩 용도로 실행될 수 있다. 따라서 실제 주문 실행 단계에서는 동일 게이트를 적용하되, 워크플로우의 주체만 다를 뿐이다.

**중복 방지 방안**:
- 제안된 n8n 워크플로우는 **현재 주문 차단 상태에서는 페이퍼 트레이딩 또는 시뮬레이션 모드**로만 운영한다.
- 실제 주문 게이트가 통과되면, 기존의 Hermes cron 기반 감시 워크플로우와 연동하여 **주문 실행은 단일 경로**(예: trading-runner 또는 스켈핑 봇의 검증된 버전)를 통해 이루어진다.
- 또는, n8n 워크플로우가 생성한 매매 신호를 기존의 `signal_events` 테이블에 기록하고, 기존의 주문 실행 로직이 이를 읽도록 설계한다.

## 5. 중복 방지 마스터 원칙

### 5.1 시간 기반 분리 원칙
- **아침 골든 타임 (08:00-09:00)**: n8n이 주도하는 **예측 및 준비 단계** 담당
  - 뉴스/시간외 데이터 수집 → AI 분석 → 파라미터 생성 → 봇 사전 준비
- **장중 감시 타이밍 (09:00-15:30)**: Hermes cron이 주도하는 **실시간 surveillance 및 알림** 담당
  - 5분 간격 snapshot_1m 수집 → OR 평가 → 타이밍 알림 → 품질 watchdog
- **장후 분석 시간 (15:30 이후)**: Hermes cron이 주도하는 **성과 분석 및 피드백** 담당
  - 일일 리포트 → 전략 변화 후보 생성 → 사용자 승인 대기
- **뉴스 브리핑 타임 (07:00)**: 별도 전용 스크립트가 담당하는 **사전 요약** 담당
  - 간단한 뉴스 요약 → 오늘의 관심 종목 후보 압축 (주문 금지)

| AI 분석 및 의사결정 지원 | n8n + LLM | 복잡한 패턴 인식 및 요약 |
| 실시간 매매 실행 | 로컬 파이썬 봇 | 초저지연 로직 필수 |
| 장중 감시 및 알림 | Hermes cron | 간단한 규칙 기반 알림 효율적 |
| 성과 분석 및 피드백 | Hermes cron | 정해진 스케줄 기반 보고서 생성 |
| 주문 실행 최종 게이트 | 공통 (설정 파일) | 두 경로 모두 동일 게이트 참조 |

### 5.4 기술적 중복 방지 메커니즘
1. **네임스페이스 분리** 
   - Hermes cron이 쓰는 디렉터리: `~/.hermes/scripts/`, `/home/june/trading/scripts/`
   - n8n이 쓰는 디렉터리: `/home/june/n8n/workflows/` (활성화 시)
   - 스켈핑 봇: `/home/june/trading/scalping_bot.py` (공유 but 다른 목적)

2. **데이터 테이블 분리**
   - Hermes cron → `intraday_prices` (snapshot_1m 용)
   - 제안된 n8n 워크플로우 → 별도 테이블이 필요 없음 (실시간은 키움 API 직접 사용)
   - 또는, n8n 워크플로우가 생성한 신호는 `signal_events` 테이블에 기록하여 기존 시스템과 연동

3. **실행 주체 분리**
   - Hermes cron: `no_agent=true` 스크립트 실행 (경량화)
   - n8n: 에이전트 기반 복잡한 의사결정 워크플로우
   - 스켈핑 봇: 독립된 프로세스 (실시간성 보장)

## 6. 실행 계획 및 검증 단계

### 6.1 단기 실행 계획 (즉시 적용 가능)
1. **환경 변수 설정**
   ```bash
   # ~/.hermes/env 또는 시스템에 추가
   export OPENROUTER_KEY="sk-or-..."
   export NEWSAPI_KEY="..."  # 만약 뉴스 API 사용 시
   export KIWOOM_TOKEN="..."  # 기존 토큰 재사용
   ```

2. **스켈핑 봇 스크립트 생성**
   - `/home/june/trading/scalping_bot.py` 작성 (위 가이드 기반)
   - `chmod +x /home/june/trading/scalping_bot.py`

3. **n8n 워크플로우 생성 (방법 B 권장)**
   - n8n UI → New Workflow → 위에서 상세히 설명한 노드 구성대로 구축
   - initialement **Manual Execute** 로 테스트 후, 안정성 확인 시 **Activate**
   - 활성화 전, 기존 크론 작업 목록을 확인하여 시간 충돌 없음 재확인

4. **최초 테스트 실행**
   - n8n에서 **Execute Workflow** 수동 실행
   - 로그 확인:
     * 08:00: 뉴스 데이터 수집 성공?
     * 08:20: OpenRouter 호출 성공 및 순수 JSON 반환?
     * 08:45: 파이썬 봇이 인자를 잘 받아서 로그 출력?
     * 09:00: 봇이 키움 API에 로그인하고 실시간 등록 대기 상태 진입?
   - 테스트 완료 후, 필요에 따라 코드 조정

### 6.2 중기 실행 계획 (성과 검증 후)
1. **페이퍼 트레이딩 모드 구현**
   - 스켈핑 봇에 실제 주문 대신 페이퍼 트레이딩 모드 추가
   - 매매 내역을 `signal_events` 또는 별도 테이블에 기록
   - 장후 성과 분석을 통해 알파 검증

2. **기존 워크플로우와 연동**
   - n8n 워크플로우가 생성한 매매 신호를 `signal_events` 테이블에 INSERT
   - 기존의 `signal_events` 를 읽는 Hermes cron 기반 알림/리포트 시스템과 연동
   - 또는, 스켈핑 봛이 기존의 주문 실행 로직을 호출하도록 인터페이스 통일

3. **점진적 운영 시간 확대**
   - 처음에는 09:00-10:00만 운영하여 안정성 확인
   - 성과 좋으면 10:30까지 확대, eventually 풀 타임 운영 고려

### 6.3 장기 목표
